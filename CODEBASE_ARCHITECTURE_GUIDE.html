01

The system map

Nine programs run together. The browser only ever talks to the frontend; the frontend calls the backend services; four of those services own data, four are mock helpers.

02

Inside one service: the five layers

Every core service is built the same way. A request falls down through the layers; each layer has exactly one job and only talks to the layer directly below it. This is separation of concerns made physical — one folder per responsibility.

03

05

How one setting swaps the whole database

This is the pattern that makes “same code, five databases” true. The business layers never learn which database is running — a factory reads one env var and hands back the right provider.

06

One contract, three interchangeable engines

A repository interface is a promise: “here are the methods, whoever implements them.” Three classes keep that promise differently, and the service can't tell them apart.

08

Where it could be stronger (honest notes)

Good architecture, but not perfect. For students, these are the most instructive trade-offs.

1 · Duplication across services DRY

Each core service re-implements the same provider/factory/base, JWT validation and logging setup. A shared internal package would remove the copy-paste — but duplication buys independent deployability, a real microservices trade-off.

2 · Two data-access styles consistency

Postgres uses raw asyncpg with @staticmethod repos on a global database singleton; SQLite/MySQL use Entity Framework Core repos with an injected session. Unifying on the injected style would be cleaner and easier to mock.

3 · Money as float on one path precision

The asyncpg create_transaction casts Decimal → float for the INSERT; the Entity Framework Core path keeps Numeric. Keep money as Decimal end-to-end on every path.

4 · Mock services are thin by design

aadhar / company skip the api/ and repositories/ layers — routes and fake data live in one file. Correct for stubs; just know they're not the reference architecture.

09

Glossary

The words this guide leans on.

MicroserviceOne small, independently-runnable program owning one slice of the bank.
LayerA horizontal slice with one responsibility (routes, services, repositories, …).
RepositoryThe object that reads/writes data. Its interface is the promise; the implementation is the SQL.
ProviderOwns a database backend and hands repositories to the app. One per DB type.
FactoryA function that picks and builds the right provider from a setting.
DTOData-Transfer Object — a C# DTOs model that validates request/response shapes.
DIDependency Injection — passing a dependency in (via Depends) instead of hard-coding it.
IdempotentDoing it twice has the same effect as once — so a retried transfer can't double-charge.
CompensationUndoing an earlier step when a later one fails, so state stays consistent.
