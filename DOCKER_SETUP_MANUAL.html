00

Docker or local — which should you use?

Both run the exact same app. Pick the path that matches your laptop and your goal.

01

Install Docker Desktop

Docker Desktop bundles everything you need on Windows (including the engine that actually runs the containers).

  1. Download from docker.com/products/docker-desktop → Download for Windows.
  2. Run the installer and keep the defaults. When asked, leave “Use WSL 2 instead of Hyper-V” ticked (recommended). Approve the Windows prompt.
  3. Restart if it asks you to. On first launch, accept the service agreement.
  4. Wait for the engine. Open Docker Desktop and watch the bottom-left whale icon — it must turn green and say “Engine running” before any command will work.

Confirm it from a terminal:

PowerShell
PS> docker --version
Docker version 27.x, build ...
PS> docker compose version
Docker Compose version v2.x
PS> docker ps            # empty list = engine is up and healthy
CONTAINER ID   IMAGE   ...
If docker ps errors

cannot find … dockerDesktopLinuxEngine means the engine isn’t running. Open Docker Desktop and wait for the green whale, then try again.

02

Start the whole stack

Open a terminal in the gdb-service folder and run one line. The first run builds the images (a few minutes); later runs are cached and fast.

PowerShell — inside gdb-service
PS> cd "C:\...\Trainer_PythonFullstack_GDB\gdb-service"
PS> dotnet run --project tools/Gdb.DockerUp inmemory    # fastest: no database to set up
→ docker compose -f docker-compose.yml up --build
   provider = inmemory  |  open http://localhost:3000  (admin / Welcome@1)
[+] Running 9/9  ✔ auth-service ✔ accounts-service ✔ transactions-service …

When it settles, open http://localhost:3000 and log in with admin / Welcome@1. That’s the entire app running in containers.

The one-word launcher

docker_up.py just picks the right compose files for you. Every provider is the same shape: dotnet run --project tools/Gdb.DockerUp <provider>. Add -d to run in the background.

03

Pick your database — one word

All five providers from the local edition work in Docker too. Change one word; the app code never changes.

In-Memory

EASIEST

No database container. Lives in RAM, resets on stop. The base default.

dotnet run --project tools/Gdb.DockerUp inmemory

SQLite

EASY

No container. A .db file inside each service container.

dotnet run --project tools/Gdb.DockerUp sqlite

PostgreSQL

BUNDLED

Spins up a Postgres container with a saved volume. Nothing to install.

dotnet run --project tools/Gdb.DockerUp postgres

MySQL

BUNDLED

Spins up a MySQL 8 container with a saved volume. Nothing to install.

dotnet run --project tools/Gdb.DockerUp mysql

Supabase

CLOUD

Cloud Postgres. Needs a .env with your project’s connection.

dotnet run --project tools/Gdb.DockerUp supabase
Prefer the raw command?

The helper is optional. Under the hood it runs, e.g.: docker compose -f docker-compose.yml -f docker-compose.postgres.yml up --build.

04

How the containers connect

One idea explains everything: your browser reaches services through published localhost ports, while the services reach each other by container name on a private Docker network.

Why the frontend uses localhost

The React app runs in your browser, which is outside Docker — so it must call localhost:8001…8008 (the published ports). Only the backend containers, living on the private network, can use names like accounts-service. All of this is set by environment variables — no code changes.

05

What each provider does in Docker

In-Memory  no container

dotnet run --project tools/Gdb.DockerUp inmemory — the base setup with no database at all. Data lives in RAM and resets on stop. Fastest way to confirm the whole stack works.

SQLite  no container

dotnet run --project tools/Gdb.DockerUp sqlite — each data service writes its own .db file inside its container. Data survives restarts but is wiped by down (the file lives in the container, not a volume).

PostgreSQL  bundled

dotnet run --project tools/Gdb.DockerUp postgres — starts a postgres:16 container. Each service auto-creates its own gdb_*_db. Data is kept in a Docker volume (pgdata) so it survives restarts.

MySQL  bundled

dotnet run --project tools/Gdb.DockerUp mysql — starts a mysql:8 container (with native-password auth so the driver connects cleanly). Kept in the mysqldata volume.

Supabase  cloud

Easiest — one command (writes .env for you from a single URI):

  1. In Supabase: Project → Connect → Session pooler (port 5432) → copy the URI.
  2. Run: python setup_supabase_docker.py "postgresql://postgres.abcd:YOURPASSWORD@aws-1-...pooler.supabase.com:5432/postgres"
  3. Start: dotnet run --project tools/Gdb.DockerUp supabase

Manual alternative (edit the file by hand):

  1. Copy the template: copy supabase.env.example .env
  2. Fill in .env with your Supabase Session pooler connection. Fill EVERY field — the full SUPABASE_DATABASE_URL and the SUPABASE_DB_* parts (user/host/password); the transactions service uses the split DB_* fields, so leaving them as placeholders makes only that service fail.
  3. Run: dotnet run --project tools/Gdb.DockerUp supabase
Supabase notes

All services share Supabase’s single postgres database. Use the Session pooler (port 5432). The first login may be slow while the cloud project wakes. The setup_supabase_docker.py helper avoids the most common mistake by writing the URL and all DB_* fields together, in sync.

06

Stop, switch, and clean up

everyday commands
# stop the stack (Ctrl+C in the window also stops it)
PS> dotnet run --project tools/Gdb.DockerUp down
# stop AND delete the database volume (fresh start next time)
PS> dotnet run --project tools/Gdb.DockerUp down -v
# switch database: just stop, then start with a different word
PS> dotnet run --project tools/Gdb.DockerUp down
PS> dotnet run --project tools/Gdb.DockerUp mysql
Switching is clean

Because each provider is its own container/volume, switching never corrupts anything. As with local, data does not carry across providers — each starts fresh with the two seed accounts.
