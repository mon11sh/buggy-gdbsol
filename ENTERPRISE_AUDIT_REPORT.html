Executive summary

What the board should know in one minute.

GDB is a well-structured, genuinely educational microservices platform. The four stateful services (accounts, transactions, auth, users) follow a clean layered architecture (api → services → repositories → database/providers), a strong provider/factory abstraction that runs the same business code against five databases, correct password/PIN hashing (bcrypt), and a fail-closed idempotency system for money movement. Docker support is excellent.

However, judged against the "production for millions of users" bar, it is not yet enterprise-ready. Two critical security defaults (hardcoded JWT signing secret and inter-service key) would allow token forgery if shipped as-is. Operationally it is blind: no CI/CD, no metrics/tracing/correlation IDs, no schema-migration tooling (schema is (re)created at startup; two migration files are empty). Structurally there is meaningful debt: two divergent data-access styles, a sys.path source coupling to auth_service, and heavy copy-paste of infrastructure across services with no shared library.

Board recommendation: approve a phased hardening program (see Roadmap). Phase 0 (this week) must close the two critical secret-management issues and CORS wildcard before any shared/staging deployment. None of the findings require a rewrite — the foundation is sound and the fixes are additive.

Critical & High-priority issues

Each carries the board's required analysis. "Effort" is engineer-days for one senior engineer.

C-1Critical · Security

Hardcoded default JWT signing secret, shared across all services (HS256)

The same symmetric secret both signs and verifies every token, and ships as a code default.

Current state
JWT_SECRET_KEY = "your-super-secret-jwt-key-change-in-production" is the default in auth/accounts/transactions/users config/settings.py; .env.production ships a placeholder (your-production-jwt-secret-key) rather than injecting at deploy.
Problem
HS256 uses one shared secret to sign (auth) and verify (all). If the default is ever active, anyone can forge a valid role:"ADMIN" token.
Business impact
Full account takeover / unauthorized fund transfer; regulatory + reputational catastrophe for a bank.
Technical impact
Every authenticated endpoint across 8 services is trust-compromised; no key rotation path.
Scalability
Shared symmetric secret must be distributed to every replica/service — rotation becomes a fleet-wide event.
Maintainability
Secret duplicated in 4 settings files → drift risk.
Solutions: (1) Inject JWT_SECRET_KEY from a secrets manager (Vault / AWS Secrets Manager / Doppler) at deploy; fail fast if unset in non-dev. (2) Best → move to asymmetric RS256/ES256: auth_service holds the private key and signs; other services verify with the public key (via JWKS) — no shared secret, clean rotation. (3) Add a startup guard that refuses to boot in ENVIRONMENT=production with a default/empty secret.
Effort 3–5dRisk LowBackward-compat RS256 changes token issuance; roll with dual-verify windowPriority CRITICAL
C-2Critical · Security

Hardcoded default inter-service API key (shared static secret)

Current state
All 8 services default INTERNAL_API_KEY = "dev-internal-api-key-change-in-prod"; verified by plain, non-constant-time string equality on the X-Internal-API-Key header (*/dependencies/internal_auth.py). Docker compose ships the key inline.
Problem
Internal endpoints (debit/credit, PIN verify) are gated only by a guessable shared bearer secret — not mTLS. A leaked/default key lets any actor move money between accounts.
Business impact
Unauthorized internal money movement; bypass of the public auth layer entirely.
Technical impact
Timing side-channel on comparison; single secret guards the whole east-west surface.
Scalability
One shared secret across the mesh; rotation is fleet-wide and coordinated.
Security
No caller identity, no per-service scoping, no revocation.
Solutions: (1) Inject the key from secrets manager + use hmac.compare_digest for constant-time compare (quick). (2) Best → mTLS between services (or a service mesh — Istio/Linkerd) so identity is cryptographic, per-service, and revocable. (3) Interim: short-lived signed service tokens (SPIFFE/JWT-SVID) instead of a static key.
Effort 2d quick / 8–13d meshRisk LowBackward-compat Header stays; only the value/verify changesPriority CRITICAL
H-1High · Security

CORS wildcard * combined with allow_credentials=True

Current state
accounts & notification list explicit origins plus "*"; aadhar/company/payment are ["*"]; all applied with allow_credentials=True. Every .env.production sets CORS_ALLOWED_ORIGINS=*.
Problem
* + credentials is spec-forbidden and enables cross-site credentialed requests (CSRF-style data exfiltration).
Business impact
A malicious site could ride a logged-in user's session against the API.
Technical impact
Browsers may silently drop credentialed * responses → inconsistent behaviour too.
Maintainability
Origin policy scattered across 8 settings files.
Performance
Negligible.
Best → centralize an explicit allow-list (env-driven) shared by all services; never combine * with credentials. Put CORS at an API gateway (see Microservices) so it's defined once.
Effort 1dRisk LowBackward-compat Must enumerate real frontend originsPriority HIGH

H-4High · Security / Privacy

Aadhaar (national ID) stored in plaintext and returned unmasked

Current state
Stored plaintext (accounts/database/orm_models.py aadhar_number String(12)) and returned unmasked in account-detail responses (result["aadhar_number"] = savings.aadhar_number). It is masked in logs (good).
Problem
Sensitive government PII at rest without encryption and exposed over the API in full.
Business impact
Data-protection / regulatory violation (India Aadhaar Act, DPDP Act); breach liability.
Technical impact
PII sprawl; hard to satisfy "right to erasure" / audit.
Maintainability
Masking logic is inconsistent (route-level in one place, absent in the model serializer).
Scalability
PII exposure grows with data volume.
Best → encrypt Aadhaar at rest (app-level envelope encryption or DB column encryption), store a hash for lookup, and mask in all serializers (******** + [-4:]) — centralized, not per-route. Add field-level access control + audit for any unmasked read.
Effort 3–5dRisk Medium (data migration)Backward-compat Encrypt existing rows via migrationPriority HIGH
H-5High · Data / Ops

No schema-migration tooling — schema created at startup, migration files empty

Current state
No EF Core Migrations anywhere. Schema is built by Base.metadata.create_all at boot (+ raw *_schema.sql). users_service/migrations/001_add_role_column.sql and root database_setup.sql are 0 bytes.
Problem
create_all never alters existing tables — schema changes to a live DB are silent no-ops; no versioned, reversible migration path.
Business impact
Risk of data loss / drift / failed releases; no safe rollback of a schema change in production.
Technical impact
Environments diverge; can't reproduce a schema at a point in time.
Scalability
Blocks zero-downtime deploys and blue/green.
Maintainability
Empty migration files are actively misleading.
Best → adopt EF Core Migrations per service (autogenerate from the ORM models), run migrations as a deploy step (not at app startup), and delete the empty/placeholder SQL. Keep create_all only for the in-memory/dev path.
Effort 3–5dRisk LowBackward-compat Baseline-stamp existing schemasPriority HIGH
H-6High · DevOps / SRE

No CI/CD and no observability — the platform is operationally blind

Current state
No .github/workflows, GitLab CI, or Jenkinsfile. No Prometheus/Grafana/OpenTelemetry/Sentry/ELK. No correlation/request IDs. Only accounts_service has a real logging config; the other 7 use bare logging. /health exists but is wired to nothing.
Problem
No automated test/build/deploy gate; in production there is no way to see latency, errors, or trace a transfer across services.
Business impact
Slow, risky releases; incidents detected by customers, not dashboards; long MTTR.
Technical impact
No golden signals, no distributed trace of the debit→credit→gateway→notify flow.
Scalability
Can't capacity-plan or find bottlenecks under load.
Maintainability
Inconsistent logging makes debugging service-specific.
Best → (1) CI: GitHub Actions running lint + the ~629 tests + pip-audit + image build per PR. (2) Observability: OpenTelemetry SDK → traces/metrics; a shared structured-JSON logger with a X-Correlation-ID middleware propagated across integration calls; /health+/ready+/live wired to the orchestrator; Prometheus + Grafana dashboards.
Effort 8–15d (phased)Risk LowBackward-compat AdditivePriority HIGH

01Architecture & separation of concerns

Score 6.0 — a clean layered monolith-per-service; missing the enterprise cross-cutting tissue.

Strengths
  • Textbook layering in the 4 stateful services: api → services → repositories → database/providers; routes thin, services hold rules, repos own all SQL (no SQL found in any service).
  • Strong provider/factory + repository-interface (ABC) abstraction — same code, five databases (OCP/LSP/DIP in practice).
  • Database-per-service (local); inter-service calls isolated in integration/ HTTP clients.
  • Custom exception hierarchy; DTO validation at the edge (C# DTOs).
Weaknesses / smells
  • Inconsistent structure — two tiers (4 full vs 4 thin mock services); DB_* vs DATABASE_* env naming; asyncpg-vs-Entity Framework Core divergence.
  • No shared library → infra copy-pasted (M-3); sys.path source coupling (M-4).
  • PIN-lockout orchestration leaks into the route layer instead of the service.
  • Not Clean/Hexagonal/Onion/DDD in the strict sense — it's classic layered; no ports/adapters or domain model isolation, no bounded-context contracts beyond HTTP DTOs.

Clean/Hexagonal/Onion/DDD verdict: the dependency direction is mostly correct (business logic doesn't import web/DB frameworks — except the asyncpg global), which is Onion-ish. To reach Hexagonal, formalize ports (the repo/integration interfaces already are proto-ports) and adapters, and lift domain entities out of C# DTOs/ORM types.

03API design

Score 6.5 — solid REST + Swagger; let down by cross-service inconsistency.

Good
  • Consistent /api/v1 versioning; proper status codes (201/404/409/422/423 Locked with Retry-After).
  • C# DTOs request models + response_model on most routes; rich Swagger tags/summaries; custom OpenAPI JWT security scheme (accounts/txn/users).
  • Idempotency-Key header on all money movement; internal/public separation.
Fix
  • Three different error-response shapes (M-8).
  • Prefix/docs-path inconsistency: /api/v1/internal vs /internal/v1; /api/v1/docs vs /docs; API_PREFIX vs API_V1_PREFIX.
  • Accounts list not paginated; no sort params anywhere; some routes return bare dict (no response_model).
  • aadhar/company raise HTTPException(detail=str(e)) — unstructured errors.

04Database

Score 6.0 — thoughtful portable schema and pooling; migration strategy is the gap (H-5).

  • Schema: sensible indexes + unique constraints + FKs with ON DELETE CASCADE (accounts), Numeric(15,2) money, portable types (Integer autoincrement, String not native ENUM) so one model runs on 5 engines.
  • Pooling: Entity Framework Core pool_pre_ping (mysql uses pool_recycle to dodge an aiomysql/Entity Framework Core-2.0.23 bug); asyncpg pool min5/max20.
  • Idempotency table + fail-closed flow; providers auto-create their DB.
  • H-5 no EF Core Migrations; create_all can't evolve a live schema; 2 migration files empty.
  • No explicit pool_size/max_overflow tuning; per-operation sessions mean multi-step money moves aren't one DB transaction (documented TOCTOU window); no eager-loading (N+1 latent on list/log endpoints).
  • transactions diverges: raw asyncpg for postgres/supabase, DB_* env, global singleton (M-2).

05Security

Score 4.0 — good primitives undermined by default secrets and PII exposure. See C-1, C-2, H-1…H-4, M-5…M-7.

Done right
  • Passwords & PINs bcrypt-hashed (rounds 12); no plaintext secrets in storage.
  • Parameterized SQL ($1,$2); the one f-string query is whitelisted + bound (not injectable, but fragile).
  • RBAC enforced via Depends; brute-force throttle on login + PIN; Aadhaar masked in logs.
OWASP gaps
  • A02 Crypto failures: default JWT/PIN keys (C-1, M-6 Fernet key from weak default).
  • A05 Misconfig: CORS *+creds (H-1), DEBUG=True, no security headers.
  • A06 Vulnerable components: python-jose 3.3.0 (H-3).
  • A01/A07: shared static internal key (C-2), per-process throttle (M-5).
  • A08 Data: Aadhaar plaintext + unmasked (H-4).

Recommended remediation roadmap

Sequenced by risk-reduction per effort. Nothing here is a rewrite.

Phase 0 · week 1 · Stop-the-bleed

Security defaults

Quick wins 1–4 + inject JWT/internal keys from a secrets store; remove .env.production from git (H-2). Exit gate for any shared/staging deploy.

Phase 1 · weeks 2–4 · Trust & correctness

AuthN/Z + money + deps

RS256/JWKS (C-1) & mTLS or signed service tokens (C-2); upgrade vulnerable deps + Dependabot (H-3); Decimal end-to-end (M-1); encrypt + mask Aadhaar (H-4).

Phase 2 · weeks 3–6 · Operability

CI/CD + observability + migrations

GitHub Actions (lint+tests+audit+build); OpenTelemetry + correlation-ID middleware + structured logging; wire health/ready/live; EF Core Migrations per service, migrations as a deploy step (H-5, H-6).

Phase 3 · weeks 6–10 · Consolidation

Shared library + consistency

Extract gdb_common (auth, providers, logging, errors, secure-headers) → kills M-3/M-4; unify data-access on Entity Framework Core (M-2); standard error schema + prefixes (M-8); Redis-backed throttle/idempotency (M-5); pagination everywhere (M-9).

Phase 4 · quarter 2 · Scale-out

Gateway, resilience, eventing

API gateway (CORS/auth/rate-limit centralized); retries+circuit breakers; Saga + Transactional Outbox over a broker for the transfer flow; Kubernetes + Helm; coverage gate + E2E/load tests.

Recommended target architecture & structure

Target platform

  • Clients → API Gateway (TLS, CORS, JWT verify via JWKS, rate-limit, routing).
  • Services stay stateless behind the gateway; RS256 tokens from auth, verified with public keys.
  • East-west via mTLS/service-mesh; resilient clients (retry+breaker+timeout).
  • Transfer flow → Saga + Outbox over Kafka/Redis Streams; Redis for shared throttle/idempotency/cache.
  • OpenTelemetry everywhere → traces/metrics/logs with a correlation ID; Prometheus + Grafana; EF Core Migrations-managed schemas; Kubernetes + Helm; secrets via Vault/K8s Secrets.

Recommended repo shape

# monorepo with a shared package libs/ gdb_common/ # auth(JWKS), providers, # logging, errors, headers services/ accounts/ transactions/ auth/ ... app/ api/ # adapters (HTTP) domain/ # entities + rules (pure) services/ # use-cases ports/ # repo/integration ifaces adapters/ # db, http clients migrations/ # EF Core Migrations platform/ gateway/ k8s/ helm/ observability/ .github/workflows/ # CI/CD
12-Factor / Cloud-Native gaps to close: III Config (secrets in git → externalize), XI Logs (bare logging → structured streams), V Build/release/run (no CI/CD, no immutable release tags), IX Disposability & health (wire probes), X dev/prod parity (create_all vs real migrations). Backing services (DBs) and stateless processes are already close to compliant.
